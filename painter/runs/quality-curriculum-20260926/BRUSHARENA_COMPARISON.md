# BrushArena comparison, 2026-09-27

This is a method comparison, not an experiment result. Public sources inspected: [Surya's project write-up](https://surya.website/rling-qwen-to-paint-with-code), [BrushArena's method](https://brusharena.art/method), [live run](https://brusharena.art/live), [p5.brush source](https://github.com/acamposuribe/p5.brush), and [Modal's independent flower-RL reproduction](https://gym.modal.dev/tutorials/paint_flowers). BrushArena's public gallery exposes the JavaScript for individual published works; its live API exposes painting thumbnails, prompt groups, raw judge scores, and step timing. I found no public BrushArena trainer, reward-judge, or Puppeteer harness repository. Modal's code is an independent reproduction, not BrushArena's implementation. Public work-code reuse rights were not established from the site's terms; learn from the method rather than copying published sketches.

Surya reports a prompt -> complete p5.brush sketch -> sandboxed Puppeteer render -> judge -> GRPO loop. The original nine-part reward plateaued on flat clip-art flowers. He reports that several aesthetic/adherence terms were correlated 0.85–0.95, the code-length term had saturated, and the useful variance was underweighted. The revised reward uses compile-and-actual-brush (0.05), length (0.05), HPSv3 (0.30), and a pairwise visual judge against hand-rated paintings (0.60). The pool included 117 “love” images from 1,664 manually rated generations, plus lower-tier and supplementary examples. He also reports prompt optimization converging on a short brush-method allowlist rather than a long API reference. These are reported findings for a narrow flower/watercolour task, not a validated reward for our mixed text/photo curriculum.

BrushArena's public ranking contract is 600×600 WEBGL p5.js/p5.brush, one code program per brief, no visual feedback and a common seed/retry schedule. This differs from our intended render-inspect-revise trajectory. Its public live step snapshot showed 16 prompts with 16 painting slots each; this is display evidence, **not** an optimizer-batch or GPU-utilization measurement. The live judge-score scale and internal reward implementation are not documented there.

Our pinned renderer uses p5.js 2.3.2 and p5.brush 2.2.1 in an offline Playwright/Chromium sandbox. The visual medium and canvas size are therefore already close. The 595 hash-pinned valid canvases in `teacher600-visual-audit-v1` provide an operational comparison. The reproducible [static medium audit](audit_brush_medium.py) of their exact `program.js` files found **75/595 with no brush painting call**: they call `brush.load()` but draw with native p5 primitives. All 75 are text tasks from Sol seed/wave2/wave3/wave4. Another 193 programs contain native p5 drawing calls alongside brush calls. **Zero of 595 call `brush.scaleBrushes()`**, whereas BrushArena's published contract requires `brush.scaleBrushes(3)` and the p5.brush documentation recommends scaling built-in brushes to a 600×600 canvas. Static call sites are not executed mark counts, but the 75 no-brush cases are clear failures of a brush-medium gate. The earlier source audit had already flagged this problem in the first Sol text batch.

The render metadata for all 595 records gives a median painting time of 31.96 seconds and p90 of 171.87 seconds (photo median 42.46, text median 25.88). The 75 no-brush programs have median 2.6 seconds versus 37.0 seconds among 520 programs with a brush painting call. Those groups differ in author and complexity; **the difference is descriptive, not a causal estimate of p5.brush overhead**. Five further photo programs remain censored at 600 seconds. These CPU/SwiftShader timings do not establish BrushArena's renderer speed on its hardware.

The highest-value transfer is the taste anchor, not a new drawing library. For the next bounded test, freeze a small mixed set of identical text and photo inputs, teacher/model, seed, renderer and attempt budget. Compare our current contract with a short, explicit brush allowlist, `brush.scaleBrushes(3)` in setup, and a concrete layering/opacity instruction. Record compile rate, actual brush-use rate, render time and blinded visual preference for the same inputs. Do not silently change and re-label old program renders: scaling changes marks, so every proposed output must be rendered and judged against its own baseline. Do not use code length as a quality reward in the current no-speed phase. A brush-use gate is a data-contract check, not proof of beauty.

For RL, build a **human-calibrated, category-matched** exemplar bank before applying pairwise judgments. For photo tasks, show the source photo in the comparison and require subject/layout fidelity alongside beauty. A generic beautiful flower should not beat a faithful bus merely because it resembles a global “love” pool. Compare corrected work to its exact prior canvas as a separate turn-improvement measure; retain the prior and the judge's concrete weakness. Test judge repeatability and order swaps on manually rated controls before trusting it as reward. The current 595-case Luna pass is mode-confounded and cannot seed this bank automatically. A distinct speed curriculum can follow only after visual quality improves.
