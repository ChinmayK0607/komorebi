# Reflection-guided painting RL and renderer throughput — 2026-09-27

## Research question and baseline

Can source-grounded criticism followed by one visual revision improve painting quality under an online RL objective without making rendering the limiting stage? Compare every result with the same frozen initializer, task, turn/token allowance, renderer revision, seed, and source image or exact text brief. The initializer for the next SFT canary is the public photo-SFT step-512 adapter pinned in `P5_SFT_DECISION.md`. No new SFT or RL result is claimed here.

The relevant paper is Lee et al., [*Reinforcement Learning from Reflective Feedback*](https://arxiv.org/pdf/2403.14238) (2024). It samples several responses, selects promising ones, gives a fine-grained critique, samples refinements, and trains on chosen/rejected examples with DPO. It is an NLP study, not a demonstration that a painter can self-correct, and its exploration used up to 30 candidates and large separately trained feedback/reward models. We should transfer the **critique-guided exploration** idea, not its candidate count, compute budget, or claim that DPO is the only suitable optimizer. Their own limitations include subjectivity in feedback and exploration cost.

For painting, show the critic the actual rendered canvas and the true source. Ask for one or two concrete weaknesses (e.g. missing object, wrong silhouette, confusing depth, muddy contrast) plus a strength to preserve. Keep the final reward a source-matched pairwise visual preference for beauty **and** fidelity; the critique guides the next action and diagnoses failures, rather than becoming an additive score the model can game. Preserve rejected and unchanged revisions. At each state, compare candidate actions conditioned on the *same* prompt/canvas/history; a first-turn program and a revision program have different states and are not a valid direct DPO pair. Online RL may use trajectory outcome and turn-improvement signals, with censored renders and judge disagreements accounted for separately.

## Renderer evidence

The frozen renderer `painter/vendor/integrations/watercolour/renderer.py` launches a fresh unprivileged Python worker and sandboxed Chromium for **each** program, loads pinned p5.js/p5.brush, runs one 600×600 canvas in offline SwiftShader, and records elapsed and painting seconds. Fresh-process isolation is a useful safety property. Its per-render startup/teardown overhead is visible in the receipts; removing it is an optimization experiment, not an assumed safe drop-in change.

The earlier 595 valid raw first paints had median painting time **31.96 s**, p90 **171.87 s**; five more photo programs were censored at 600 s (`BRUSHARENA_COMPARISON.md`). Those programs mix author, complexity and medium, so this is a workload distribution, not a direct renderer benchmark. In the first three collected ten-scene repair shards (Flash `00`, `01`, Pro `00`), **98 attempted renders** have median wall **5.41 s**, p90 **10.92 s**, maximum **16.80 s**; median painting time **2.71 s** and median wall-minus-painting overhead **2.75 s**. These values come from exact `turn-*.json` renderer receipts in the publicly hash-verified shard bundles. The workload changed toward clearer opaque forms with sparse brush accents, so the 5.41 s figure must not be projected onto arbitrary future policy samples. The 30 scenes contain 82 valid rendered turns; validity and visual quality are separate.

Inference/judging and rendering need separate timing windows. During the previous photo RL run the inference GPU was almost fully busy while trainer time included long collection waits (see root `RESEARCH_LOG.md`), but no run-wide fraction of wall time attributable to rendering is available. Do not describe the pipeline as render-bound or saturated from a single `nvidia-smi` snapshot. The current MiMo API generation has often taken minutes per turn, substantially longer than these particular render attempts.

## Execution sequence

1. **Finish data and one strong SFT canary.** Review all valid repair turns against the exact first paint and source; keep source fidelity and painterly beauty as separate labels, preserve failures. Train one balanced LoRA continuation on reviewed text/photo first paints plus coherent render-conditioned revisions, preserving the full previous program in revision inputs. Use the exact frozen inference template. A second SFT run is allowed only to fix a specific observed failure; then scale RL rather than cycling SFT repeatedly.
2. **Begin quality RL at one turn while throughput work proceeds.** Sample multiple programs per source, render with the production contract, compare source-matched canvases pairwise, and use a small human-calibrated judge anchor. Do not add a stroke, token, or speed reward until quality is reliably better. Track novelty, validity, judge disagreement, rejected/censored fractions, update pace, and matched blind visual preference. This stage can start without waiting for a new renderer architecture.
3. **Add one inspect–revise turn before a long-horizon rollout.** Feed the model its real canvas, full prior program, source, and a grounded weakness/preserve-strength critique. Render the revision and keep both canvases. Compare two-turn against one-turn at matched total token/compute budgets, and measure how often the second turn actually improves the image. Only then consider three or more turns. A second turn with no visual information gain is wasted compute.
4. **Measure, then optimize the render tail.** On a CPU Linux VM, replay the same hash-pinned representative set of student/teacher programs with renderer concurrency 1/2/4/8 where hardware permits. Report median/p90/p99 service time, queue wait, timeouts, CPU and memory, completed valid canvases per wall-hour, and exact PNG hashes. Cache only exact `(program hash, seed, renderer/assets revision, canvas contract)` results; never reuse a lookalike program's canvas. Add a fast syntax/contract preflight only if it rejects actual invalid programs without rejecting valid canvases. If Chromium startup is material, test a prewarmed worker with a **fresh isolated browser context per sketch**, bounded worker lifetime and kill-on-timeout; require pixel/hash parity and security review against the fresh-process baseline before adoption. Do not silently change the renderer during matched training or evaluation.
5. **Pipeline CPUs and GPUs.** Put render workers on CPU capacity independent of the inference/trainer GPUs, overlap render/judge with generation, and size queues to observed service times and CPU/memory limits. The new-shard median would make two turns plausible at modest CPU parallelism, but the old 172 s p90 demands tail management. Re-evaluate on-policy program complexity before increasing RL horizon. Report GPU busy fraction over a stated window with denominator, separately for inference and trainer, and completed quality-evaluable updates per dollar.

The stage transition is evidence, not a rigid stop gate: if a two-turn pilot is slower but visibly better, keep it as a quality route while the one-turn route sustains training throughput. After quality stabilizes, introduce the separate speed/budget curriculum requested by the user.
