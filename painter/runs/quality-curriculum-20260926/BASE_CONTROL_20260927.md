# Fresh-base brush demonstration control — 2026-09-27

**Hypothesis:** The 467 renderable brush demonstrations plus 173 retention rows can teach the pinned Qwen3.8-27B base model a useful painting policy without relying on the prior photo-SFT adapter. This tests whether the data contains learnable task signal; it does not prove that the data is visually optimal.

**Matched baseline:** untouched `Qwen/Qwen3.8-27B` revision `1d4bf0f2ff6012fd82039f2fa52739d0dd7c60c0`, evaluated on the frozen 28-photo manifest SHA-256 `9943878cc43d48f1cf9ff60e5af633089bf2bd8d45141216531363cad8f1c878` with the same two-turn, 32,768-context inference protocol as the new adapter. Compare also with the prior photo-SFT step-512 and brush-SFT step-40/160 results as historical context, noting that their earlier two-turn evaluations used a shorter 16,384 context and are not exactly matched.

**Fixed data:** Public `CK0607/komorebi-painter-teachers`, revision `ac13a35b966c6af397b509b6496c58f9bbdcefaf`, path `curricula/teacher600/brush-sft-20260927-v1`. Training JSONL SHA-256 `5d74c7eacb31370a1befb42c8499d6775c1021f68d7fc889fe017b96bff3ec51`; validation SHA-256 `080535a0d8669401ac663ba1719b5839b9f5d9c20efd8440d778c35d96ed3735`. The packaged copy is locally hash-verified before transfer. Prime RL revision `26b3131d2716a4f8210b165df584b83b4bc54f61`.

**Method:** A newly initialized rank-16, alpha-32 LoRA on the exact pinned base; frozen vision encoder, fresh AdamW optimizer, one example per sequence, assistant-only cross-entropy, no target truncation, batch 4, 160 optimizer updates, constant `3e-6` learning rate. The same 640 rows and order as the brush-SFT pass are used. This learning rate is higher than the previous `1e-6` fine-tune because a fresh adapter has no prior painter weights; optimizer settings are therefore not a strict single-variable comparison. Public, hash-verified LoRA exports at step 0, 40, 80, 120 and 160 are required. The [node runner](base_control_node.sh) performs exact processor and public-repository checks before any optimizer update. The [evaluation runner](base_control_eval.sh) compares untouched base, step 40 and step 160 on the same 28 cases.

**Pre-run diagnosis:** Prior step-512-initialized brush SFT lowered token loss from 0.574 to 0.149 and modestly improved render validity, but preliminary Luna-low comparison favored the initializer visually on most jointly rendered cases. Among 640 scheduled rows, only 91 are first-turn photo painting, matching the held-out task; 215 are first-turn text painting, 161 are render-state revisions, and 173 are retention. The 306 first paints include 298 provisional visual-B and only eight A examples. Revisions were verified renderable, not demonstrated pairwise improvements. The 467 painting targets have a median 11 `brush.*` calls, so the missing visual gain is not explained by absence of brush calls. The assistant target is a plan plus complete JavaScript; roughly 96.5% of its characters are code. Cross-entropy rewards teacher-token agreement, not beauty, fidelity, or improved pixels. These are candidate explanations, not causal conclusions.

All **306 first-paint targets use exactly the same one-sentence plan**: “Paint the reference with a coherent silhouette, color, and brush texture.” Thus first-turn plan tokens carry no example-specific structural analysis. Across 467 painting targets there are 148 distinct plans, mostly in revisions. The training conversations are state-complete three-message examples; revisions include the prior image and program in the user turn, while evaluation uses the full assistant history. This state representation difference may also hurt revision behavior and requires a separate matched test.

Training embeds reference/canvas views with the long edge reduced to at most 448 pixels to fit the 16,384-token window. All 28 frozen evaluation photographs have an original long edge of 500–640 pixels and are sent at their original dimensions, another train/eval input-resolution difference. The vision encoder is frozen, but the LoRA still learns from image-conditioned language states; this mismatch should be controlled before attributing residual quality differences to optimizer choices.

The 36 validation rows are foundation/procedural tasks (for example, `sphere-003-turn-1`), rather than held-out real-photo first paints. Validation token loss therefore checks the language objective and procedural retention, not the visually important photo distribution. The external frozen rendered evaluation is the only current photo-quality readout.

The exact processor audit counts **1,341,136 supervised assistant tokens** across 640 training rows: 118,477 (8.8%) in the 91 initial photo paints, 290,928 (21.7%) in 215 initial text paints, 836,600 (62.4%) in 161 canvas-conditioned full-program revisions, and 95,131 (7.1%) in 173 retention rows. These are token counts, not an exact decomposition of optimizer gradient weight, but they expose a task mismatch: the held-out test emphasizes first paintings from photos while most target tokens teach long rewrites of a prior canvas. The vision/reference image, previous canvas, system instruction, and user request are supplied as context and excluded from the cross-entropy target. The assistant's plan, complete JavaScript program, and end-of-message token receive teacher-forced next-token loss. No pixel, fidelity, aesthetic, or turn-to-turn improvement score enters this SFT objective.

All 467 painting targets are full `javascript` code-block actions and **zero** are `FINISHED` actions, even though the interaction contract permits finishing after inspecting a good canvas. The SFT thus does not demonstrate when to stop editing; extra revisions can damage a satisfactory first paint. This is a concrete coverage gap, separate from the visual quality of any single teacher program.

**Preflight failure and repair:** The earlier package archive was internally hash-consistent but contained the *pre-final* training JSONL (`94a9151e…`, not the final `5d74c7ea…`). Its exact processor audit stopped on a 16,963-token row before the trainer began, with **zero optimizer updates**. The final train JSONL, validation JSONL, and manifest were transferred separately and hash-checked on the node. The runner now requires the exact final three hashes, not just internally consistent package contents. Its bootstrap/model-staging steps reuse the verified staged artifacts on retry. The old package is a source carrier only; the final data hashes above define this experiment. This bootstrap failure and its charged setup time belong in the cost accounting.

**Decision rule:** Do not promote solely on lower loss or syntactic validity. Evaluate first-turn and final rendered validity for all 28 cases, inspect side-by-side canvases, record any censored render/context failures, and make a visual pairwise comparison against the untouched base and the prior step-512 painter. If the base control learns syntax but not compelling visual structure, use the data as initialization and prompt/reference curriculum for visual RL only after choosing a stronger quality-filtered subset and a credible pairwise reward. Do not treat demonstrations as an RL reward by themselves.

A negative fresh-base result is **not** proof that every teacher painting is bad: this is one epoch of only 467 painting targets, with just 91 matching first-turn photos, on a 27B model. It can falsify the narrower claim that this particular finite SFT recipe alone bridges the base-to-teacher gap. The user-approved next quality phase should start from whichever frozen painter checkpoint actually wins the visual comparison, not automatically from this fresh-base adapter.

The frozen 28-photo, two-turn, 32k-context comparison completed for all three policies with exit 0 and no provider or context-length failures. Untouched base produced **2/28 valid first** and **9/28 valid final** canvases; fresh-base step 40 produced **8/28 first** and **14/28 final**; step 160 regressed to **4/28 first** and **9/28 final**. The first-turn response lacked a complete JavaScript block in 8, 8, and 12 cases respectively; all eight base and step-40 cases and seven step-160 cases used an HTML fence, while the remaining step-160 no-code cases include plan-only or incomplete replies. The 56 or fewer calls per policy had zero, zero, and four `length` finish reasons, so output cap explains only part of step-160's format failure. Unsupported API calls, including `brush.ellipse` and `brush.lineBleed`, also occur; neither API string appears in the 467 training painting targets. They are model extrapolation to nonexistent names, not direct imitation of teacher programs. The step-160 result is a contract and rendering regression despite steadily lower procedural validation loss (0.427 before updates, 0.411 near step 40, 0.346 after step 160).

The visual spot review is mixed and is **not** a blinded 28-case preference study. This supports an early code/structure gain and later regression, not a claim that step 40 is consistently beautiful or that every step-160 painting is worse. The previously liked photo-SFT step-512 painter remains the practical quality default; its older evaluation used a different context protocol and is not a fully matched statistical comparator here.
